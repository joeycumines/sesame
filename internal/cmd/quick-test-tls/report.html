TLS ClientHello Impersonation — Test Report

Engine ceilings & documented gaps (context)
  • Go engine (crypto/tls, wire-proven Go 1.27): cipher_suites/supported_groups are membership filters over fixed internal preference orders; session_id always 32 bytes; legacy_version always 0x0303; no GREASE, sigalg, extension-order, or padding control. Honors a spec only on exact match, fails closed otherwise.
  • Builtin TS engine (Bun/Node node:tls): all capabilities false — any non-default spec dimension fails closed. Bun node:tls sends record version 0x0301 and omits status_request(5)/SCT(18); Bun fetch (the opencode reference) sends 0x0303 with both.
  • Opencode fidelity: opencode ships Bun; matching its ClientHello exactly is the job of the planned native BoringSSL N-API addon (ts-native-addon). The endpoint under Bun already matches on extension order, groups, session_id, ALPN, and GREASE-absence.
  • Browser fidelity: full Chrome ClientHello fidelity (arbitrary extension order + GREASE placement) needs a manual ClientHello builder behind the same engine contract — out of reach for both builtin engines by design.
